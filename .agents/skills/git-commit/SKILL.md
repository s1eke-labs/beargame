# Git 提交规范

## 提交时机与检查

- 每完成一个可独立说明和验证的功能或修复，都应在相关检查通过后立即提交，不把多个无关功能积攒到最后一次提交。
- 提交前查看 `git status`、工作区差异和暂存区差异，明确本次改动范围及已有的无关改动。
- 按改动选择相关检查：逻辑或数据变更运行 `npm test`，构建相关变更运行 `npm run verify`，交互变更运行相关 `qa/` 测试并按需使用浏览器验证实际交互。纯文档改动检查内容、引用路径及格式即可；本技能改动还应验证 YAML 元数据。
- 检查失败时先修复本次引入的问题。若环境缺失或已有问题导致无法完成验证，说明具体阻碍和未验证项，不把它宣称为已完成且验证通过；不要为了满足提交频率而提交未完成的功能。

## 提交范围

- 使用明确的文件路径或 `git add -p` 选择性暂存；避免直接使用 `git add .`、`git add -A` 或 `git commit -a` 混入无关改动。
- 保留用户及其他任务的改动，不覆盖、回退或擅自清理。暂存区已有无关改动时先确认归属并隔离提交范围；无法安全分离时停下说明，不擅自取消他人的暂存。
- 不提交密钥、凭据、真实 `.env`、依赖目录、`dist/`、缓存或临时验证产物，遵守现有 `.gitignore`。必要且与本次功能相关的依赖清单和锁文件可以提交。
- 提交前复核最终暂存差异，确保提交只包含本次功能或修复及其必要测试、文档。

## 提交说明

格式为 `type: 中文简述`，需要范围时使用 `type(scope): 中文简述`。标题与可选正文都使用中文；类型名称和必要的函数名、文件名、API 等代码标识符可保留英文。范围优先使用中文，确需对应代码模块时可用其原名。

- 常用类型：`feat` 新功能、`fix` 修复、`refactor` 重构、`test` 测试、`docs` 文档、`style` 格式、`perf` 性能、`build` 构建、`ci` 持续集成、`chore` 维护。
- 标题简洁说明具体变化，不使用“更新代码”“完成修改”等空泛表述；正文按需解释原因、关键行为及验证结果。
- 示例：`feat: 添加小熊职业筛选`、`fix(交互): 修复刷新后的多标签页占用`、`docs: 增加中文 Git 提交规范`。

## 完成与权限边界

- 提交后查看最新提交和 `git status`，确认目标改动已记录；交付时报告提交哈希、中文摘要、验证结果及相关遗留项。无关改动仍可保留在工作区，不以清空工作区为目标。
- 没有本次实际改动时不创建空提交。
- 本规范要求创建普通提交，不授权 `push`、强制推送、修改远端、`commit --amend`、变基或其他历史重写，也不授权删除他人改动；需要这些操作时另行取得用户授权。用户明确要求暂不提交时遵循其最新要求。
